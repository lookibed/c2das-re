# metrics Architecture

Read `ARCHITECTURE_COMMON.md` (repo root) first - its contract binds this document. The folder
measures how readable the converter's output is: it converts a fixed set of C programs and
counts, per emitted module, `unsafe` scopes and expressions, pointer steps and indexes,
`reinterpret` casts, `goto` and labels, raw `while` loops and literals a name exists for. The
counts ratchet like the suite pass lists, in the opposite direction: a total only goes down.
The readability criteria, compliance percentages against a human port measured over the same
inputs' text, are `ARCHITECTURE_CRITERIA.md`.

## 1. File charters

- `readability.das` - the driver (`scripts/run_readability.sh`): takes the input keys (section
  2), runs one worker process per input, `--jobs` at a time (4 by default), through
  `run_workers` of `suites/suite_runner.das`, the pool the csmith driver uses; a worker
  (`--one <input key>`) converts the input through `convert_input` of `readability_inputs.das`
  into `work/<input key>/das/` and writes its counts to `work/<input key>/counts.txt`. The
  driver gathers the files, prints the totals table with the inputs attempted and failed, and
  applies the ratchet (section 4). A failed worker's line carries what the worker printed. It
  never runs a converted module.
- `readability_inputs.das` - an input key converted: it writes or generates the input's C file
  and converts it through `converter/pipeline.das` under the `linux` dialect (section 2); the
  criteria driver converts through it too.
- `readability_count.das` - the counting: `count_module` compiles one emitted module and walks
  its AST (section 3), counting what the module's own file spells and, when it is a cluster
  module, what the fragments it is given spell (`converter/ARCHITECTURE_LAYOUT.md`); `count_text`
  and `read_count_text` are the worker file.
- `readability_file.das` - the capture as data: the metric and input group names, the text of
  `readability_linux.json` (top-level keys sorted, two-space indent, one module per line with
  its metrics sorted), its reader, the shape check and the input-key check the gates run, the
  ratchet's decisions (the committed column, when `--update` is honoured, the exit code), and
  the totals table, rendered through daslib's `md_boost` `render_md_table` like the perf
  report, so both paste into a progress log as they are. It requires nothing beyond daslib,
  since the review walker runs `REVIEW.das` without the module folders loaded.
- `readability_linux.json` - the committed capture: `inputs` (the module count per group),
  `modules` (input key to its ten counts) and `totals` (their sum).
- `REVIEW.das` - the gate over the capture: its shape (the three top-level keys, every input
  group and metric present as a non-negative integer, the totals the sum over the modules, each
  input count its group's module count, the text the writer's own spelling of it), its module
  keys the expected input keys (section 2), and nothing tracked under `work/`.
- `tests/` - the dastest suite: hand-written das programs under `tests/fixtures/` that exercise
  every counter, the negative cases of each definition included; the worker on a kernel and on
  two inputs that fail; the gate on a broken capture; the capture's text, checks, ratchet
  decisions and table. The preflight tests lane runs it.
- `work/` - converted output, gitignored.

The capture is written by its own writer, not daslib's `write_json` the perf capture uses:
`write_json` indents with tabs and writes a table's keys in hash order, and a file a diff
reads line by line wants them sorted.

## 2. Inputs

An input key is `<group>/<id>`, the groups `c_testsuite`, `csmith`, `gcc_torture`, `lua` and
`perf`.
The expected input keys are `expected_input_keys` of `suites/suite_files.das`: every id a
suite's `expected_pass.txt` lists that its `skip.txt` does not, and every kernel under
`perf/kernels/`, three times: `perf/<kernel>` converted under the defaults,
`perf/<kernel>@copy` under `--param-writes copy` and `perf/<kernel>@while` under `--loops while`
(`converter/ARCHITECTURE.md` section 1), so each non-default form's readable cost is measured
beside the default; and each Lua program of `lua/sources.das`, three times: `lua/<program>` converted
from the release's files in the source layout, its counts the sum over its modules (a cluster
module's fragments counted with it, the link module's wrappers too), `lua/<program>@scc` in the scc
layout and `lua/<program>@single` in the single layout. A program of
one file is one module in either layout, so every other input stands for both. The committed capture
holds exactly those keys: both `REVIEW.das` gates, this folder's and `suites/`, check it, so a diff to a ratchet list fails the suites gate until the
capture is re-recorded, and a run without `--filter` names a recorded key no list holds any
more. A c-testsuite or torture id is its fetched `.c` file; a csmith seed is generated by
`csmith_program` of `suites/csmith/generate.das`, the generation and header splice the
differential driver runs; a kernel is composed by `write_composed` of `perf/perf_compose.das`,
the program the perf harness builds, and an `@copy` or `@while` key composes the kernel its id
names before the suffix (`kernel_of_key`).

A run over every input takes about 5 minutes for the c-testsuite alone in one worker at a
time; the torture suite has four times its inputs and a csmith seed converts in 5 to 60
seconds, so a serial run takes over an hour and the run is parallel by default.

## 3. The counting definitions

A module is compiled with `compile_as_written` of `converter/pipeline.das`: every `unsafe`
scope kept (`no_fold_unsafe`), no optimization, and every symbol kept (`export_all`; the
compiler otherwise drops a global or a private function nothing uses before the walk sees it),
so the AST is the text's own. The walk
visits the module's enums, globals and functions and counts only what the module's text
spells: a node whose location is another file (a macro's wrap, a `c_runtime` generic's body)
is not counted, nor is a function the compiler generated (the `[c_union]` accessors) or the
emitter's per-module `[init] c2das_dialect`. A generic the module defines is counted once:
through its first instance when it has one, since one instance per call signature would count
its text again, and as written when it has none. A generic without an instance is not
inferred, so it gets only the counters that read the parser's nodes: `c_function`,
`unsafe_block`, `unsafe_expr`, `reinterpret`, `goto`, `label` and `literal_named`; the pointer
counters and `while_rangeable` need types it does not have.

- `c_function` - a function carrying the `c_function` annotation.
- `unsafe_block` - an `unsafe { }` block. The emitter writes none; the count stays as the
  check that it does not.
- `unsafe_expr` - an `unsafe(...)` expression. daslang keeps no node for it: the parser flags
  the wrapped expression `userSaidItsSafe`, and that flag is what counts. Inference turns
  `unsafe(p + i)` and `unsafe(p - i)` into a pointer-step call without the flag, located at its
  operator (`probes/test_ast_facts.das`), so a pointer step also counts when the nearest open
  parenthesis before its operator follows the word `unsafe`.
- `pointer_arith` - a pointer step: daslang infers `p + i`, `p - i`, `p - q`, `p++`, `p--`,
  `p += i` and `p -= i` into calls of the `i_das_ptr_` builtins, and each call counts once. The
  `addr(a[0]) + end_index(k, N)` form is one of them.
- `pointer_index` - an index into a pointer: `deref` of a pointer step (`deref(p + i)`, the
  emitter's spelling of C's `p[i]`) or `[]` on a pointer. The step inside a `deref` counts
  here, not under `pointer_arith`, so the two counts are disjoint.
- `reinterpret` - a cast with the reinterpret flag that the inferred program keeps. Inference
  drops a reinterpret to the type a call's result already has, so csmith's
  `reinterpret<T>(c_volatile_load(v))` of a volatile pointer global `v` of type `T` (C's cast
  away of a qualifier) is spelled and not counted, where `reinterpret<T>(v)` of a plain one is.
- `goto`, `label` - each `goto label N` and each `label N:`.
- `literal_named` - an integer literal of any width or signedness whose value is not 0, 1 or
  -1 and equals a named value of the same module: an enumerator, or a module-level global,
  `let` or `var`, whose initializer is an integer literal (a cast of a literal, `int64(77)`, is
  one after the compiler folds it) and that no function of the module writes (an assignment,
  a compound assignment, a step, its address taken or its pass to a reference parameter). The
  emitter writes a C `static const` or `const` global as such a `var` (`var private
  cn__LIMIT : int = 42`); a C global the program changes is written and names nothing. The definitions' own literals are not sites.
  The compiler folds a cast of a constant into a literal (`int(E.X)`, `int8(7)`) and an
  expression of constants into its value (`5 + 7`), so a literal is a site only when the number
  its text spells, after any casts, equals its value. `--verbose` names, per site, the first
  name in sort order that has the value. A C `#define` constant reaches the emitted module as
  its value with no name, so it is invisible here until the preprocessor's names are recovered
  (`docs/lowering-examples.md` "Preprocessor artifacts"); the count rises then.
- `while_rangeable` - a raw `while` a `range` loop could spell: its condition is `v < e`,
  `v <= e`, `v > e` or `v >= e` with `v` a local integer variable and `e` not reading `v`; its
  body's last statement steps `v` by a literal (`v++`, `++v`, `v += c` for `<` and `<=`; `v--`,
  `--v`, `v -= c` for `>` and `>=`; `c` a positive literal), or is a block whose `finally`
  holds that step alone, the emitter's `for` shape; the rest of the body writes neither `v` nor
  any variable `e` reads, where a write is an assignment, a move, a clone, a compound
  assignment or a step whose target is rooted at the variable (through fields, indexes and
  `deref`), its address taken, or its pass to a reference parameter; it holds no `continue`
  outside a nested loop, except in the `finally` shape, where a `continue` still runs the step
  as a range loop's does; and when the body can `break` or `return`, no statement after the
  loop in its block reads `v`, since a range loop's variable ends with the loop. A call in
  `e`, and a write through a pointer to what `e` reads, are not seen.

What the definitions leave out: the emitter spells a `for` whose body holds a `continue` and
leaves the loop early with the `_f` increment-first flag, and a `while` with a side-effecting
condition as `while (true)` with the test and a `break`; neither shape is counted, so
`while_rangeable` undercounts those loops. A `for` with no `continue` takes its increment as the
body's last statement (`converter/ARCHITECTURE_EMITTER_LOOPS.md`), a counted shape: a loop whose
counter outlives it (csmith's `for (i = 0; i < 8; i++)` over a function-level `i`) is counted
there and stays a `while`, since only a counter the `for` declares becomes a range loop. daslang's `range` has no step and does not count down, so a counted
loop stepping by `c` or downwards needs its trip count computed to be spelled as a `range`.

## 4. The ratchet

A run prints one table, the metric, the committed total, this run's total and the signed
delta, under the count of inputs attempted and failed. The committed column sums the committed
counts of the modules this run measured, so a `--filter` run compares like with like and an
input new to the ratchet counts from zero. The run exits 1 when an input failed to generate,
convert or compile, or a worker was killed past 900 seconds; when an asked `--update` is
refused (a `--filter` run or a run with a failed input never records); and, without
`--update`, when a total went up or a recorded input key is no longer expected. It exits 2
when a suite is not fetched and 0 otherwise; `--update` records a raise or a dropped input and
names it.
