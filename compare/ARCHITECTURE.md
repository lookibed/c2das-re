# compare Architecture

Read `ARCHITECTURE_COMMON.md` (repo root) first - its contract binds this document. The folder
holds the head-to-head of ledger item P8.1: c2das-re against the Rust translator lookibed/c2das
on the same inputs - the three suites, the perf kernels, Lua and, once P6 exists, PureDOOM - with
the same runner, oracle and machine for both. The Rust translator is a C2Rust fork that writes
daslang; this repository never builds it inside a test and never vendors it.

## 1. File charters

- `rust_translator.das` - the Rust translator as a child process: where its binary is, the
  commit its checkout is at, a translation of one C file (`translate_file`) or of a compilation
  database (`translate_db`) into a `RustTranslation`, the compilation database writers for a list
  of C files (`write_compile_commands` with defines, `write_unit_commands` with clang arguments),
  and a run of a translation's entry module under one execution tier (`run_translation`). It
  classifies nothing and reads no suite.
- `suite_compare.das` - the suites comparison (section 5): the suites as it runs them, their
  ids and tags, one case judged (`judge_case`, `judge_translation`, `judge_csmith_program`), the
  verdict file, the driver over the workers (`drive_suite`) and the capture's `suites` section
  (`suite_capture`, `write_capture`). It never writes under `suites/`.
- `perf_compare.das` - the perf comparison (section 8): the kernels it times (`perf_kernels`),
  one kernel through both sides (`compare_kernel`), the Rust side's entry (`rust_entry`), a lane's
  cell or error (`lane_entries`), the geometric means (`lane_geomean`, `geomeans`) and the
  capture's `perf` section (`perf_section`). It times through `perf/perf_measure.das` and composes
  through `perf/perf_compose.das`; it copies neither.
- `quality_compare.das` - the quality comparison (section 10, `ARCHITECTURE_QUALITY.md`): the corpus
  (`quality_corpus`), one key measured on both sides by a worker (`measure_key`), the Rust side's
  `c2da_` declarations split into its runtime and program code (`c2da_blocks`, `split_runtime`), the
  function extraction (`function_text`), the totals and the `quality` section.
- `lua_compare.das` - the Lua comparison (section 9): the translation of the interpreter, the gap
  (`program_gap`) and the `lua` and `doom` sections.
- `projects.das` - the real projects of the Rust repository's `tests/manual` through both
  translators, and their entries of the `projects` section (`ARCHITECTURE_PROJECTS.md`).
- `run.das` - the command line, run from the repository root with both module folders loaded:
  `--suites` or `--suite <name>`, `--perf`, `--quality` and `--lua` (each a run of its own) with
  `--samples`, `--filter`, `--jobs`, `--out`, `--verbose`, the worker modes `--one <suite>/<id>` and
  `--one quality/<key>`, and `--lua-from <folder>`, which gives `--lua` the `.c` files of a folder
  (its `lua.c` holding `main`) and its `lua.c2das`, when present, as the sidecar (no defines without
  one; never Lua's) in place of Lua's release, translated into `<folder>/work`; `--lua` takes no
  `--filter`; `--project <name>` runs one real project with `--samples`; `--readme`
  and `--report <path>` render the capture `--out` names (section 11), in a run of their own. Exit
  0 when it ran, 2 when the Rust translator or an input (a suite's, a project's, Lua's release) is
  missing, 1 on a bad command line, an unreadable capture, an unreadable sidecar or a README
  without the compare markers.
- `compare_render.das` - the capture as markdown (section 11, `ARCHITECTURE_REPORT.md`): the
  suites, perf, size and counters tables, the functions side by side, Lua and Doom, the real
  projects, and where the Rust translator is ahead (`compare_report`); it reads and writes no file.
- `results_linux.json` - the capture (section 7): generated by `run.das`, committed, read by the
  comparison tables.
- `tests/` - `test_rust_translator.das`, the module over a stand-in translator: a shell script
  the test writes that records its argv, prints the real banner, and writes, refuses, stays
  silent or sleeps by the name of its input; `test_suite_compare.das`, the suites comparison over
  a stand-in that refuses, sleeps, or copies a das program the test writes, the programs and their
  compile checks run on the real daslang; `test_perf_compare.das`, the perf comparison over
  kernel folders, cells and captures the test writes, a stand-in translator, and one lane timed on
  the real daslang over a das program printing a kernel's line; `test_quality.das`, section 10 over
  captures, das modules and a stand-in translator the test writes, one kernel converted for real;
  `test_lua_compare.das`, section 9 over stand-in Rust sources, a stand-in program of two C files
  with its sidecar, an `nm` and a translator the test writes, and `--lua --lua-from` run to its end
  over them, never reading the fetched Lua release; `test_projects.das`, the real projects over a
  stand-in project and translator the test writes; `test_compare_render.das`, section 11 over
  captures the test writes, and `--readme` and `--report` run in a scratch folder; `_common.das`,
  what they share.
- `work/` - gitignored scratch: translations, compilation databases, the runs' builds and each
  case's folder `work/<suite>/<id>/` (the translation `das/`, the run's `run/`, a csmith
  program generated there, the `verdict`), and each perf kernel's `work/perf/<key>/` (the composed
  program and the native build, our conversion and its builds `ours/`, the Rust translation
  `rust/` and its builds `rust_run/`), each quality key's `work/quality/<key>/` (the C file,
  `ours/`, `rust/`, the worker's `quality.json`), and `work/lua/` (the compilation database, the Rust
  translation `rust/`, the gap's objects `obj/`), and each real project's `work/projects/<name>/`
  (`ARCHITECTURE_PROJECTS.md`).

## 2. The Rust translator

A Rust translation is the set of `.das` and `.das.inc` files the binary
`c2dascript-transpile` writes into one output folder for one C program. Its pins are in
`VERSIONS.md`: the lookibed/c2das commit, the rust toolchain its `rust-toolchain.toml` names,
LLVM 18, and the daScript commit lookibed/c2das's CI runs its own output on. That daScript is a
fork commit, 3 commits ahead of an upstream master older than this repository's pin; the Rust side's output runs here on this repository's
daScript, so both sides run on one daslang.

`scripts/build_c2das_rust.sh` clones the checkout when it is absent, refuses one at another commit
than the pin unless `--allow-other`, checks rustup, the toolchain and `llvm-config-18`, and builds
the release binary; `--check` builds nothing. The binary the module runs is `$C2DAS_RUST_BIN`, else
`target/release/c2dascript-transpile` under `$C2DAS_RUST`, else under `/root/c2das` (`rust_binary`).
The commit a capture records is the `HEAD` of the git work tree holding the binary, accepted only
when that tree has `c2dascript-transpile/Cargo.toml` (`rust_version`).

## 3. The entry module {#entry}

Under `--libc std` the translator renames C's `main` to `main_0` and adds a wrapper,
`[export] def main() : int`, that turns the daslang command line into C's `argc` and `argv`
and calls `main_0` (at the pinned commit: `c2dascript-transpile/src/translator/functions.rs`
lines 315-322, `translator/libc.rs` `build_main_wrapper` at line 5792 and its declaration named
`main` at line 6020). A C `main` with more than two parameters is refused under `--libc std`
(`translator/libc.rs` line 1541). The printer writes every function as `def <name>(<params>)`,
parentheses always (`das_ast/src/stmt.rs` lines 245-250), so a line opening `def main(` marks
the wrapper and a line opening `def main_0(` does not.

The module daslang runs is the file holding the wrapper when it is a `.das` module, and the
cluster module `<stem>.das` when it is a fragment `<stem>.das.inc`; `<stem>` keeps every dot
but the extension's, as the translator's own stems do (`lib.rs` lines 578 and 1096-1099). One C
file under `--file` becomes `<output folder>/<file name>` with its extension replaced by `.das`
(`lib.rs` `output_path_for`, lines 569-581). Under `--module-layout source` a unit outside any
cycle is its own `<stem>.das`, and a unit in a cycle is a fragment `<stem>.das.inc` included by
its cluster module; the cluster holding C `main` takes the entry unit's stem as its name
(`lib.rs` lines 1224-1230). A translation has one wrapper, so a translation with two modules
defining `main` is a failed one. Every file of the output folder is the translation's, so a
translation runs only into an absent or empty folder: the caller chooses a fresh one, and a
folder that holds anything is refused before the translator runs, its files left as they are.

Since the wrapper is daslang's default entry `main`, no `-main` is passed in any tier. The
wrapper takes C's arguments from after a `--`, else from after the script, so
`converter/tiers.das`'s `run_tier`, which passes `--` before the program's arguments and nothing
when there are none, runs a Rust translation unchanged under the interpreter, the JIT, `exe` and
`aot`; the test runs the interpreter. The `aot` host hands its whole command line to the runtime
(`das::setCommandLineArguments`) and the tier runs the binary with `--` before the arguments, so
there too the wrapper takes what follows `--` (`translator/libc.rs` lines 5835-5852). The `aot`
tier is checked on the real binary with the suites and the projects. A Rust translation requires
only daslib and its own modules, so it runs with no module folder loaded.

## 4. The command line {#command-line}

`translate_file` runs `<bin> --file <c> --libc std --strict --output-dir <out> <flags> <clang
args>`; `translate_db` runs `<bin> <compile_commands.json> --libc std --strict --module-layout
source --runtime-module <name> --output-dir <out> <flags>`, without `--runtime-module` when no name
is given (the translator names the module). The translator takes each of its own options from
anywhere in its argv and drops every `--` before handing the rest to clang
(`c2dascript-transpile/src/main.rs` lines 295-298 and 311-314, `take_flag` and `take_value` at
lines 326 and 410), so no separator is passed: it would protect no clang argument.

The translator prints the banner `c2dascript-transpile v<version>` to stderr first (`main.rs`
line 10) and progress lines to stdout as it goes: `Transpiling <stem>` and `Wrote <path>` for a
file, `Reading <path>` and `Transpiling <module>` in the source layout (`lib.rs` lines 524, 602,
652, 682 and 812). Clang's warnings reach the same output. It exits 2 on a failed translation,
with `translation failed: <error>` (`main.rs` lines 423-441), and on a refused option (`main.rs`
lines 190 and 217), and 1 on a usage error (`main.rs` lines 253-321). The child's stdout and
stderr arrive merged, so a `RustTranslation`'s `error` is the `translation failed:` line, else
the first non-empty line that is neither the banner nor a progress line, else `exit <code>`; it
is `timed out after <seconds> s` past the timeout.

## 5. The suites comparison {#statuses}

`run.das --suites` runs the Rust translator over the inputs the three suites run here: every
`.c` file of the c-testsuite and gcc-torture test folders (`C_TESTSUITE_TESTS`,
`GCC_TORTURE_TESTS`), and every csmith seed the csmith ratchet or ledger lists. Each id carries a
tag: `ours` when the suite's `expected_pass.txt` lists it, `skipped` when its `skip.txt` does,
`unlisted` otherwise, so a table can show the Rust side passing an id this repository skips.

One worker process per id, `--jobs` at a time, through the suites' `run_workers` and
`spawn_one`. The worker loads both module folders, since `converter/tiers.das` requires
`converter/dumper_a.das`, which requires the native module `crt`; the translation it runs needs
none. A case is translated by `translate_file` (`--libc std --strict`, no other flag or clang
argument), its entry checked by `daslang -compile-only` with no module folder, then run under the
interpreter by `run_translation` with `-no-module-cache` (a case's module is compiled once, so a
cache record would only churn the cache the test lanes share) and the suite's own timeout (60 s c-testsuite, 20 s
gcc-torture, 300 s csmith), and judged by the suite's oracle: c-testsuite the merged output
`<id>.c.expected` holds and exit 0, gcc-torture exit 0 with the output not judged, csmith the
native build's output (section 6) and exit 0, all through `compare_output`.

A case ends in the first status that applies, in this order: `refused` (the translator failed
within its limit, or no module defines `main`; the reason is the translation's `error`), `compile` (the
compile check exited non-zero; the reason is its first `error[` line), `timeout` (the translator
past 300 s, the compile check past 120 s, the run past the suite's timeout), `exit` (the run exited non-zero), `output` (the run printed other
than the oracle), `pass`. A csmith seed whose reference fails is `native`, which judges no translator: csmith
refuses the seed or runs past 120 s, gcc refuses the program, or the native run exits non-zero or
runs past 2 s. A worker that exits without a verdict is `crash`, and one the driver kills past the
sum of its children's limits and a 60 s margin is `timeout`; csmith's and the native run's limits
enter that sum for csmith alone. The compile check is its own step because a `daslang` run that
does not compile exits 1, as a program returning 1 does: the probe of `daslang -compile-only` on a
module naming an undefined variable exits 1 with an `error[30838]: can't locate variable` line,
and on a Rust translation that compiles exits 0 running nothing. The worker writes `work/<suite>/<id>/verdict`, one line of status, reason and
seconds, tab-separated; the driver reads it when the worker exits.

The tables' column for this repository is the ratchet: `expected_pass.txt` lists exactly the ids
its own runner passes under the same runner, oracle and machine, and the full preflight tier
re-proves it, so the comparison never reruns this repository's suites.

## 6. The csmith reference {#csmith-char}

A seed's program is the one the csmith suite's own run left in `suites/csmith/work/<seed>/<seed>.c`
when present, else `csmith_program` writes it into the case's folder; the program depends on the
seed alone (`suites/ARCHITECTURE.md`). The reference is gcc at `-O0 -fwrapv -w`, the suite's flags
without `-funsigned-char`, with the suite's 2 s native limit. The Rust translator's `char` is
`int8` whatever clang is told: `char c = 200; printf("%d", c)` translated and run prints `-56`,
with and without `-funsigned-char` among the clang arguments, while this repository's `linux`
dialect makes `char` unsigned. Each translator is judged against the native build of the `char`
model it implements.

## 7. The capture {#capture}

`results_linux.json` holds one section per comparison. A run rewrites only the entries of the suites
it ran inside `suites`, keeping every other suite and section; a `--perf` run replaces the `perf`
section whole (section 8), keeping the others, as `--quality` replaces `quality` and `--lua` `lua`
and `doom`, and `--project` sets its project's entry of `projects`, keeping the other projects; a
`--filter` run writes nothing. Each entry carries the stamps of the run that wrote it, since a run
over one suite keeps the others' entries from earlier runs. A suite's entry:

- `rust_commit` - `rust_version` of the binary, "" when it has none, with `rust_commit_error`
  saying why (the run logs it as a warning); `daslang` - the first line of `daslang -version`, as
  the perf capture records it; `date`; `cpu` and `box`, the CPU model and the `--box` name else
  the CPU's box (`perf/boxes.das`), as every section records them;
- `ids` - the cases run; `ours_pass` and `ours_skipped` - the ratchet's and the ledger's id counts;
- `rust` - the count per status, every status present;
- `rust_pass_of_ours`, `rust_pass_of_skipped`, `rust_pass_of_unlisted` - the Rust passes per tag;
- `seconds` - the suite's wall time;
- `outcomes` - one `{id, tag, status, reason, seconds}` per case, sorted by id.

## 8. The perf comparison {#perf}

`run.das --perf` times every kernel of `perf/kernels/` and `perf/kernels/dasprofile/`, nineteen,
through both translators. A kernel's key is its file stem, `dasprofile/<stem>` for the second
folder, since the two folders share stems. Each kernel is composed by the dasProfile method
(`perf/perf_compose.das`'s `composed_method_source`: the steady clock, the `volatile` sink, the
0.5 s budget) into `work/perf/<key>/<stem>.c`, and that one C text feeds all three builds:

- `native` - the pinned clang at `-O3` with `-DC2DAS_NATIVE`, which compiles the clock's C body,
  `clock_gettime(CLOCK_MONOTONIC)`; its result is the oracle.
- ours - the file converted for `linux` without the define, so the clock is the CRT's
  `c_monotonic_ns`, run with both module folders loaded.
- Rust - `translate_file` with `-DC2DAS_NATIVE` as a clang argument and a 600 s limit: the
  translator lowers `clock_gettime` but not `clock`, so the default method's program, which
  calls `clock`, is refused under `--strict`, and the method's program is not. Its entry runs
  with no module folder.

Both sides are measured in the same run with the same `--samples` (five by default), so the two
columns come from one machine state and one set of parameters; the perf folder's own captures
are never read as our side. The das lanes are `interp`, `jit`, `exe` and `aot`, each side's
measured as perf measures its lanes (`perf/perf_measure.das`): each sample its own process, the
cell the median with the spread, and a cell stands only when its result is the oracle's,
otherwise it is an error cell `result <x> differs from the native <y>`. `exe` and `aot` build
through `perf/perf_lanes.das`'s `build_exe` and `build_aot`, which load both module folders; a
program that requires neither runs the same with them loaded, so the Rust output builds there
unchanged, and a build that leaves no binary is that lane's error cell with the build's line. A
lane that has no cell is `{"error": <line>}`, never dropped: its own line, else the step every
lane stands on (`convert: ...`, `no native result: ...`). A refused Rust translation is `{status:
"refused", error}` with no lanes; one with no module defining `main` is refused the same way.

Each das lane of both sides has `COMPARE_LIMITS`: 120 s a sample, 300 s an `exe` or `aot` build
with the run it ends with, past which the lane is an error cell naming the limit (perf's own
limits, 600 s and 3600 s, fit programs that always end). The Rust translator drops `volatile` from
a file-scope object (`static volatile int depth = 31;` becomes `var depth : int = 31`), so under
the JIT nothing stops the optimizer from hoisting the kernel's work out of the budget loop; the
loop's per-run time then stays under its 1 ns floor, the count grows by one a round, and the
program never ends: the Rust `fib_recursive` under `daslang -jit` runs past 60 s, while the
native build of the same C text ends once its 0.5 s budget is spent. The Rust side's cells thus
time a program the optimizer may reshape; the oracle checks the result only, and the 120 s sample
limit is what catches the endless loop.

The section `perf` is `{cpu, box, platform, versions {clang, daslang}, rust_commit, rust_commit_error,
samples, timestamp, lanes, kernels, geomean}`. `lanes` is `native` and the four das lanes;
`kernels` maps each key to `{native, ours: {lane: cell}, rust: {status, error?, lanes?}}`, a cell
as the perf capture writes it (`time`, `spread`, `count`, `result`, `samples`). `geomean` maps
each das lane to `{ours, rust, kernels}`: the geometric mean of each side's lane time over the
native time, over the `kernels` kernels where native and both sides' cells stand, so the two means
cover the same kernels; with none both are 0.

Verified on the binary at the pinned commit: `c2dascript-transpile --file fib_loop.c --libc std
--strict --output-dir o -DC2DAS_NATIVE` over the method's composition exits 0 (with `warning:
Skipping type decl __time_t` lines), and `daslang o/fib_loop.das` prints the native build's result
`1781508648`; `sieve` likewise prints `78498`; `qsort_cmp` is refused with exit 2. A missing input
file makes the binary panic (exit 101, `thread 'main' panicked at 'Could not canonicalize ...'`),
which reaches the translation's `error`.

## 9. Lua and Doom {#lua}

`run.das --lua` writes the 33 files of `program_sources("lua")` (`lua/sources.das`) into
`work/lua/compile_commands.json` with the defines of the sidecar `lua/lua.c2das` (a sidecar that
cannot be read records nothing) and translates it with `translate_db` (600 s). The binary refuses
the program at its first call the `--libc std` tables do not lower, `unsupported external call:
ldexp` in `luaK_numberK`, exit 2, in about 6 s; `--libc all` and `--libc ffi` are `not implemented
yet`, and a unit under `--file` is refused at its first call into another unit. So the section `lua`
is `refused`, with no output to run, time, count or show; `ours` is `see ports`, where our Lua
numbers are. `doom` is `{status: "pending", reason: "P6"}`.

### 9.1 The gap {#lua-gap}

The gap lists every C library function Lua calls that the Rust translator lowers in no mode. Each
unit is compiled by `gcc -c -O0 -fno-builtin -fno-stack-protector` with the sidecar's defines, so
every call stays a call and the compiler adds none; the symbols `nm` lists undefined (`U`) or weak
undefined (`w`, `v`) over the objects, less every symbol one defines, is what Lua calls outside
itself, glibc's redirected names (`fopen64`, `freopen64`, `tmpfile64`, `__sysv_signal`,
`__isoc99_*`) mapped back to the C names clang's declarations keep. The known names are the string
literals left of each `=>` in five match tables under `$C2DAS_RUST/c2dascript-transpile/src/translator/`, at the pinned commit: `std_function` (`libc.rs`
line 791), `std_stream` (890), `libm_function` (987, each stem with its `float` form, 1017),
`jmp_call` (1658) and `canonical_runtime_function` (`runtime.rs` line 131: the `malloc` family and
`mem*`); `functions.rs` line 1234 refuses any other external. `__ctype_b_loc` is in the gap: glibc's
`isalpha` family expands to it, and the translator's own test asserts it unknown (`libc.rs` line
8523).
